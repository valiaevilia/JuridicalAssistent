# Роль L: подготовка вопроса и проверенный ответ

Реализован самостоятельный модуль L, который подключается к результатам поиска R и клиенту LLM роли B. Поиск, HTTP-сервер, веб-интерфейс, Docker и сабмиты относятся к другим ролям. Импорт модулей не читает базу, не вызывает модель и не требует ключа.

Проверены приложенное ТЗ, PDF кейса, `planchik.md` (архитектура, контракты и раздел 6), `openapi.yaml`, внешний технический регламент, стартер, разрешённые зависимости, демо и исходные выдержки базы. Внешние материалы не изменялись. В базе 21 документ; статья 152 ТК РФ уже присутствует, в отличие от пометки в плане. Записка № ЮО-7 действительно содержит инструкцию для ИИ с подменой срока оплаты. Это недоверенный текст, а не инструкция к выполнению.

В репозитории не было конфигурации LLM: существующий `openapi.yaml` описывает HTTP API. Он сохранён. Настройки L находятся в новом `llm_config.yaml`; `requirements.txt` скопирован побайтно из разрешённого списка организаторов. Код роли L использует стандартную библиотеку; только чтение YAML требует разрешённую PyYAML. Offline-пример и основной набор тестов передают `LConfig()` явно и работают без сторонних пакетов.

## Быстрая проверка

Из корня репозитория:

```powershell
python -X utf8 -m unittest discover -s tests -v
python -X utf8 -m examples.offline_demo
```

Пример использует ручной демонстрационный фрагмент и `ScriptedLLM` с заранее записанными ответами S1/S6/S8. Это проверка подключения и обработки результата, а не настоящий поиск и не измерение качества модели.

Вход: `Какой срок оплаты по договору № П-17/2024?`

Результат:

```text
Товар оплачивается в течение 30 календарных дней с даты подписания УПД на соответствующую партию (Договор поставки № П-17/2024, п. 4.2).
status = answered
```

Сверка ручных тестовых выдержек с внешними оригиналами, без изменения данных:

```powershell
python -X utf8 -m examples.verify_materials --data-dir "путь к папке data"
```

Путь передаётся аргументом; кириллица и пробелы поддерживаются. Эта команда сверяет 20 небольших выдержек с ZIP, наличие известной инъекции и формат 18 демо-вопросов. Она не проверяет юридическую полноту всех демо-ответов и не является оценкой реальной LLM.

## Подключение к B и R

```python
import time
from answer import prepare_query, answer, to_api_response
from config import load_config

cfg = load_config()  # llm_config.yaml → переменные окружения
deadline = time.monotonic() + cfg.q_budget_sec

# client_b, detect_entities_r, extract_dates_r и retrieve_r предоставляет команда.
qinfo = prepare_query(
    messages,  # строка или [{"role": "user"/"assistant", "content": "..."}]
    client=client_b, config=cfg, deadline=deadline,
    entity_detector=detect_entities_r, date_extractor=extract_dates_r,
)
retrieval = retrieve_r(qinfo)
result = answer(qinfo, retrieval, deadline, client=client_b, config=cfg)

csv_answer = result.text
http_response = to_api_response(result)
```

Сигнатуры:

```python
prepare_query(text, *, client=None, config=None, deadline=None,
              entity_detector=None, date_extractor=None) -> QueryInfo
answer(qinfo, retrieval, deadline=None, *, client=None, config=None) -> AnswerResult
```

`QueryInfo`, `Chunk`, `RetrievalResult`, `AnswerResult` — общие dataclass из `schemas.py`, с полями плана. Дополнения имеют значения по умолчанию. В частности, `RetrievalResult.quarantine: list[str]` передаёт карантин R явно. Параллельной системы типов нет; `dataclasses.asdict()` пригоден для сериализации результата.

R передаёт:

- Уникальный `chunk_id`, `doc_id`, `doc_title`, `locator` и чистый нормативный `text`. Идентификатор должен различать редакции. Метки `Д1`, `Д2` создаются L на время операции; точное соответствие есть в `debug.label_map`.
- `doc_kind`, `edition`, `valid_from`, `valid_to`, `changed_on`, `future_changes`, остальные метаданные плана. `notes` и `index_text` не используются как нормы или доказательства.
- `signals`, `warnings`, `as_of`, `editions_used`, `quarantine`. Известные сигналы перечислены ниже. L не выбирает редакцию вместо R.
- Необязательный `entity_detector(query) -> dict` с полями `docs`, `ambiguous`, `laws`, `numbers` и `date_extractor(user_context) -> list[dict]`. Формат даты: `{"text": "августе 2024", "iso_from": "2024-08-01", "iso_to": "2024-08-31", "role": "signing"}`; роли: `event`, `signing`, `delivery`, `spec`, `other`. Callback дат получает только реплики пользователя.

Без callback сущности остаются пустыми. S1 может дать проверяемые подсказки дат; месяц/год остаётся диапазоном, точный день не выдумывается. При сбое S1 `rewritten = last_user`; callbacks R продолжают работать. Реплики ассистента помогают раскрыть контекст, но не становятся доказательством фактов и дат события.

B получает `AnswerResult(text, status, query_type, claims, missing, warnings, debug)`. Статусы: `answered`, `partial`, `refused`, `out_of_scope`. Каждый итоговый `claim` содержит `text`, `doc_id`, `chunk_id`, `doc_title`, `locator`, `quote`. Служебный JSON не выводится в `text`.

### Расхождение существующего HTTP-контракта и плана

В `openapi.yaml` ответ называется `answer`, ссылки — `citations`, а статуса `partial` нет. Чистая функция `to_api_response()` преобразует `text → answer`, `claims → citations`, `chunk_id → fragment_id`, `missing → missing_info`; `partial → answered` с непустым `missing_info`, `mixed → manipulation`. Исходный `AnswerResult.status` сохраняется. Сервер B может использовать этот адаптер до согласованного изменения HTTP-контракта с F. `latency_ms` адаптера измеряет этап `answer`; полную задержку с поиском измеряет B.

### Клиент LLM

`schemas.LLMClient` задаёт синхронный контракт:

```python
chat(messages, *, json_mode=False, temperature=0.0,
     max_tokens=None, timeout=60.0) -> LLMResult
```

`LLMResult` содержит `text`, `finish_reason`, `usage`. Обычная строка или объект SDK без адаптации контракту не соответствуют. При отсутствии клиента генерация выдаёт `ConfigurationError`. Тестовый `examples.offline_client.ScriptedLLM` выбирается только явно, никогда через автоматический запасной путь.

Имена моделей, URL, ключи (`LLM_MODEL`/`GEN_MODEL`/`OPENAI_MODEL`, `LLM_BASE_URL`, `LLM_API_KEY` и алиасы стартера), HTTP и транспортные повторы реализует B. В L они не читаются и не логируются. B обязан ограничивать **весь** `chat`, включая транспортные повторы, переданным `timeout`. L не может принудительно прервать синхронный клиент, который игнорирует этот контракт.

`deadline` — конечное абсолютное значение `time.monotonic()`, не Unix-время и не длительность. Передавайте один дедлайн через S1, R и `answer`. Локальный бюджет начинается при S1 и сохраняется в `QueryInfo.debug`; L выбирает минимум локального и внешнего дедлайнов. Таймаут каждого вызова не превышает остаток бюджета. Поздний ответ после дедлайна отбрасывается. Для параллельной обработки каждый вопрос должен иметь собственные `QueryInfo`, `RetrievalResult` и безопасный для потоков клиент B.

Обычный путь — S1, S6, S8. Не более одного повтора JSON и одного S9. Исправление проходит S7 заново и, если хватает бюджета, новую S8. Лимит пяти LLM-вызовов включает S1; транспортные повторы внутри клиента B в этот счётчик не входят, но входят в его timeout. При нехватке времени/вызовов S8 пропускается, S7 сохраняется.

## Проверки и политика выдачи

| Проверка | Реализация |
|---|---|
| C1 | Цитата — подстрока именно указанного чанка после нормализации пробелов, регистра, `ё/е`, кавычек и тире. Fuzzy не используется. Проверяются границы слов и очевидная потеря соседнего отрицания/ограничителя. |
| C2 | Существование метки, соответствие `doc_id/chunk_id/title/locator`, локаторы, номера договоров и распространённые обозначения законов в утверждении. Каноническую ссылку формирует код из R. |
| C3 | Числа, даты и единицы каждого claim сверяются с **его цитатой**. Другой чанк, вопрос пользователя и предыдущий ответ не подтверждают число. Поддерживаются основные русские числительные, группировка тысяч, миллионы, десятичная запятая, проценты, даты ISO/ДД.ММ.ГГГГ/число-месяц-год. |
| C4 | Названия организаций, названия в кавычках, типичные ФИО, ИНН, части адресов и ключевые должности сверяются с цитатой и названием её документа. Это ограниченные шаблоны, не полноценный NER. |
| C5 | Карантин не отправляется модели. Подозрительные строки исключаются без удаления отдельных слов из нормы; легитимные строки сохраняются. Выявляются директивы на выходе и числа с единицами, имеющиеся лишь в карантине. Число `90` само по себе не запрещено. |
| C6 | Статус соответствует доказательствам и `missing`; свободный `answer` не добавляет текст сверх claims. Финальный ответ строится из проверенных claims, не из произвольного `answer`/`assumptions`/`missing` модели. |
| C7 | Обязательные оговорки R проверяются и затем гарантированно добавляются шаблонами кода, если помещаются в лимит. При превышении лимита выдаётся явный технический отказ вместо усечения оговорки. |
| C8 | Ограничения длины и разметки. В финале удаляются целые утверждения со ссылками, а не куски цитат; при сокращении меняется статус и появляется пояснение. |
| C9 | Только bounded AST с числами и `+-*/()`, `Decimal`, без `eval`, имён, вызовов, степеней. Все константы должны иметь input с подтверждённой цитатой и значением; проценты допускают перевод в долю. Результат сверяется отдельно. |
| C10 | Русский язык при русском вопросе: проверка наличия и преобладания кириллицы. Стилистическую корректность оценивает S8. |

`validate_answer()` возвращает `ValidationReport` с результатом и причинами каждой C1–C10, индексами нарушивших claims, проверенными цитатами и расчётами. В `AnswerResult.debug.checks` находится последняя S7, `violations` сохраняет типы найденных нарушений, в том числе исправленных. C7 в S7 может оставаться отрицательной: шаблоны добавляются при S10, без лишнего вызова модели.

S8 — отдельный JSON с оценкой **всех** индексов claims (`full/partial/none`), пропущенных частей, ложной предпосылки, редакции и выдуманных фактов. Неполная или противоречивая самопроверка не принимается. S8 не может отменить S7.

Если S8 отключена, не состоялась или обнаружила ошибку, свободные `claim.text` не используются. Резервный режим показывает целые исходные нормативные фрагменты R, с цитатами, ссылками и оговоркой о неподтверждённой полноте/применимости; статус `partial`. Это сохраняет условия за пределами короткой цитаты модели. Если ни одной пригодной цитаты нет, выдаётся отказ. Ошибка клиента, JSON или дедлайна обозначается технической причиной, а не отсутствием информации в базе.

`missing` самой модели не выдаётся как установленный факт отсутствия нормы. Конкретные недостающие документы и редакции берутся из R; для остальных неподтверждённых частей используется осторожное пояснение. Это сознательно консервативная политика до проверки целевой модели.

### Сигналы R

Поддерживаются `older_edition_missing`, `future_edition_missing`, `edition_missing`, `explicit_ref_missing`, `text_missing`, `entity_unknown`, `doc_expired`, `doc_not_yet_effective`, `renewal_unconfirmed`, `ambiguous_boundary`, `as_of_assumed_current`, `date_matters`, `ambiguous`.

```python
signals = {
    "edition_warnings": [
        {"code": "older_edition_missing", "reference": "ТК РФ, ст. 70", "before": "2026-09-01"}
    ],
    "as_of_assumed_current": True,
    "date_matters": True,
    "ambiguous": ["D2", "D3"],
}
```

Также принимаются прямые ключи сигналов и строки вида `older_edition_missing:ТК РФ, ст. 70 до 2026-09-01` в `warnings`/`edition_warnings`. Для конкретных оговорок R должен передавать подробности, а не только `true`. Кандидаты `ambiguous` — список doc_id или объектов с doc_id. Нужны доказательства по каждому кандидату; простого перечисления имён недостаточно. `entity_unknown` запрещает подмену похожим договором. При несовпадении даты события с `valid_from/valid_to` L дополнительно ограничивает применимость, но не выбирает новую редакцию.

`topic_not_in_base`, `coverage`, `top_score`, `gap`, `quarantine_hit`, `editions_used` сохраняют смысл контракта R. Произвольный порог отказа по скору не введён: для него нужны реальные результаты dev/holdout.

## Настройки

Значения YAML переопределяются env. Неизвестные параметры, неверные типы, NaN, бесконечности и недопустимые лимиты дают `ConfigurationError` без вывода переданного значения.

| YAML | Env | По умолчанию |
|---|---|---|
| prompt_version | L_PROMPT_VERSION | L-1.0 |
| s8_enabled | S8_ENABLED | true |
| max_repairs | MAX_REPAIRS | 1, разрешено 0–1 |
| json_retries | L_JSON_RETRIES | 1, разрешено 0–1 |
| max_llm_calls | L_MAX_LLM_CALLS | 5 |
| answer_hard_limit | ANSWER_HARD_LIMIT | 9500, максимум 9500 |
| max_input_chars | L_MAX_INPUT_CHARS | 60000 |
| max_context_chars | L_MAX_CONTEXT_CHARS | 24000 |
| max_tokens | MAX_TOKENS | 2500; env не опускает ниже 1500 |
| max_tokens_ceiling | L_MAX_TOKENS_CEILING | 5000 |
| temperature | TEMPERATURE | 0; максимум 0.2, S1/S8 всегда 0 |
| llm_timeout | LLM_TIMEOUT | 60 секунд |
| q_budget_sec | Q_BUDGET_SEC | 120 секунд |
| s8_min_remaining_sec | L_S8_MIN_REMAINING_SEC | 8 секунд |

`L_CONFIG_PATH` или `load_config(path=...)` задаёт другой YAML с разделом `role_l`. Непереданный и отсутствующий YAML допускает defaults+env: регламент гарантирует перенос корневых `.py`, но не произвольного YAML. Явно указанный отсутствующий файл — ошибка. Имя модели/адрес API в бизнес-логику не зашиты.

## Что проверено и что остаётся команде

Offline-проверки используют только явно переданный `ScriptedLLM`, в интеграционных тестах подключения к сокетам запрещены. Покрыты корректный ответ, ошибочные источники/локаторы, подделка цитаты и числа, единицы, имена, пустая выдача, частичный ответ, диалоги, даты и интервалы, оговорки, инъекции, JSON, ошибки клиента, S8/S9, общий дедлайн/счётчик вызовов, ограничение длины и адаптер HTTP.

`Metrics.add(result)` / `Metrics.emit()` позволяют B вывести агрегаты в stderr: статусы, типы нарушений, доли исправлений/резервных ответов/ошибок JSON, среднее число вызовов и время этапа. Тексты вопросов, ответов и ключей в эти агрегаты не входят. Общий mutable-счётчик не создаётся при импорте.

Ограничения: точная цитата, совпавшие числа и S8 не доказывают безошибочность юридического вывода; короткая цитата может упустить далёкое исключение. Эвристики инъекций и C4/C10 не покрывают все языковые формы. Полноту поиска и выбор редакций обеспечивает R. Смысловые результаты предзаданных ответов не являются замером качества DeepSeek. Сеть/целевой API, реальные промпты на DeepSeek V4.1 Flash, качество 18 ответов целевой модели, наборы dev/holdout, доля лишних отказов, абляции и тайм-бюджет общего сабмита ещё требуют проверки B/R/L после интеграции. Вебинар отдельно не предоставлен; его пересказ в плане не использовался как подтверждённый источник требований.

Основные платформенные файлы: `schemas.py`, `config.py`, `prompts.py`, `guard.py`, `answer.py`; дополнительные: `llm_config.yaml`, неизменённая копия `requirements.txt`, `examples/`, `tests/` и этот документ. Тестовый клиент и примеры в платформенный ZIP включать не нужно. Сетевой клиент B, реализация R, сервер и frontend для проверки этого этапа не требуются.
